# Product Requirements Document (PRD)
## Project: RoboAI - Industrial Operations & Fault Troubleshooting Assistant

---

## 1. Executive Overview

### 1.1 Product Vision
RoboAI is an intelligent, domain-grounded industrial copilot designed for manufacturing plants, automation facilities, and equipment maintenance teams. It fuses **static engineering documentation** (PDF technical manuals, Standard Operating Procedures, schematic guides) with **real-time operational telemetry** (text-based machine logs, PLC fault dumps, sensor alarm streams).

By running a streamlined agentic workflow, RoboAI identifies fault codes, diagnoses operational mistakes, and delivers precise, safety-compliant troubleshooting actions with direct citations to original equipment manufacturer (OEM) documentation.

---

## 2. Target Personas & User Scenarios

### Persona A: Maintenance Technician ("Alex")
- **Profile**: Field engineer responsible for physical repairs, calibration, and routine servicing.
- **Pain Point**: When a hydraulic press or robotic arm halts with error code `ERR_HYD_403`, Alex has to search through a 600-page paper/PDF manual while production line downtime accrues ($500-$2,000/minute).
- **Need**: Upload the manual once, paste or upload the shift fault log, and immediately obtain the root cause and step-by-step resolution.

### Persona B: Industrial Automation / PLC Engineer ("Ravi")
- **Profile**: Controls engineer monitoring SCADA and PLC event streams.
- **Pain Point**: Parsing hundreds of lines of repetitive timestamped telemetry to isolate intermittent communication dropouts or threshold violations.
- **Need**: Upload raw `.txt` / `.log` files and ask: *"Highlight all anomalous pressure spikes between 14:00 and 15:30 and show what the safety manual dictates."*

### Persona C: Plant Safety & Compliance Manager ("Elena")
- **Profile**: Ensures plant compliance with ISO standards, OSHA guidelines, and operating protocols.
- **Pain Point**: Verifying whether past incident logs reflect compliance with standard operating guidelines.
- **Need**: Ask questions across historical logs and operating manuals to confirm proper emergency procedures were observed.

## 3. Core Problem Statement

Industrial operations suffer from two distinct silos:
1. **The Static Silo**: Hundreds of pages of technical PDFs and TXT files containing machine specifications, maintenance routines, and safety lock-out procedures.
2. **The Dynamic Silo**: High-volume, unstructured text logs generated by PLCs, IoT gateways, and CNC machines containing timestamps, error codes, and operational metrics.

Current generic chat tools either:
- Lack domain-specific context (hallucinating incorrect torque values or wiring steps).
- Cannot correlate raw log anomalies with vendor manuals.
- Are too complex and heavyweight to deploy on-premises or on local engineering workstations.

RoboAI solves this through a lightweight, grounded dual-stream RAG architecture.

## 4. Functional Requirements

### 4.1 Ingestion Module: Knowledge Base (Manuals & SOPs)
- **FR-1.1**: The system **MUST** accept document uploads in `.pdf` and `.txt` formats.
- **FR-1.2**: Extracted text must undergo intelligent semantic chunking preserving section headers, table structures, and safety warnings (`DANGER`, `WARNING`, `CAUTION`).
- **FR-1.3**: Chunks must be embedded and indexed in an in-memory / disk-persisted **FAISS** vector database.
- **FR-1.4**: Users must have visibility into loaded documents (filename, page count, chunk count, and deletion capability).

### 4.2 Ingestion Module: Telemetry & Machine Logs
- **FR-2.1**: The system **MUST** support uploading raw operational logs (`.txt`, `.log`, `.csv` text dumps).
- **FR-2.2**: The parser must detect standard industrial timestamp formats (e.g., ISO-8601, `YYYY-MM-DD HH:MM:SS`), severity labels (`INFO`, `WARN`, `ERROR`, `FATAL`, `CRITICAL`), and error codes (e.g., `E-104`, `ERR_MOTOR_OVERHEAT`).
- **FR-2.3**: Uploaded logs must be stored in the session state buffer, with automated extraction of the top anomalies and errors.

### 4.3 Query & Diagnostic Capabilities
- **FR-3.1 Document Q&A**: Operators can query the system about equipment specifications, operating ranges, wiring pinouts, and scheduled maintenance routines.
- **FR-3.2 Fault Diagnosis**: When log files are loaded, the system must cross-examine log errors with relevant sections in the indexed manuals.
- **FR-3.3 Prescriptive Recommendations**: Outputs must provide:
  - **Identified Fault / Anomaly**: Exact log line and timestamp.
  - **Potential Root Cause**: Why the failure occurred.
  - **Prescribed Remediation**: Sequential steps to fix the issue.
  - **Source Citation**: Specific manual name and page/section number.
  - **Safety Precaution**: Necessary lockout/tagout (LOTO) or safety advisories.

### 4.4 User Interface (UI)
- **FR-4.1**: Interactive web dashboard built with **Streamlit**.
- **FR-4.2**: Dedicated side panel / dock for:
  - OpenRouter API configuration (API key entry, model selection dropdown).
  - Knowledge Base upload zone (PDF/TXT) with index status badge.
  - Active Log file upload zone (TXT/LOG) with quick error summary chip.
- **FR-4.3**: Main viewport featuring:
  - Tab 1: **Interactive Diagnostics Chat** (conversation history, streaming responses, citations).
  - Tab 2: **Log Inspector & Anomaly Heatmap** (table view of warnings/errors detected in the active log).
  - Tab 3: **Knowledge Base Browser** (preview of indexed documents and search chunks).

## 5. Non-Functional Requirements

### 5.1 Performance & Latency
- Document indexing for a 50-page PDF manual must complete within **10 seconds** on standard CPU.
- End-to-end question answering latency should be **under 4 seconds** using modern OpenRouter models (e.g., Claude 3.5 Sonnet, DeepSeek V3, GPT-4o-mini).

### 5.2 Determinism & Hallucination Resistance
- If the queried information is not found in the uploaded manuals, the model must explicitly state: *"Information not found in the uploaded equipment manuals. Please check physical documentation or contact OEM support."*
- Prohibit hypothetical electrical/mechanical specs without grounding.

### 5.3 Simplicity & Portability
- Zero external database services (PostgreSQL, Neo4j, or Pinecone) required. The entire stack must run with `pip install` and `streamlit run app.py`.
- No complex multi-agent circular debate loops. A single, deterministic LangGraph state machine ensures fast execution and zero infinite loop risks.
